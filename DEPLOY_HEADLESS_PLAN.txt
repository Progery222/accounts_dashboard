План: деплой на headless-сервер (без монитора / рабочего стола), Playwright и парсинг
================================================================================

Цель: на проде запускать Chromium без физического дисплея, с предсказуемыми
зависимостями и настройкой через env.


--------------------------------------------------------------------------------
Фаза 0 — Зафиксировать контуры
--------------------------------------------------------------------------------

  - Записать целевой сценарий: один процесс Django + воркеры Playwright на одном
    хосте или разделение ролей.
  - Составить список всех мест, где поднимается браузер (поиск по репо:
    launch_context, chromium.launch, launch_persistent_context, headless=).
  - Отдельно отметить: фоновый скрапинг (refresh) vs интерактивный вход
    (страница «Настройки» с окном браузера).
  - Зафиксировать ОС продакшена и способ запуска (systemd / Docker / k8s) —
    от этого зависят пути к профилю и env.
  - Синхронизировать две копии worker_utils.py (backend/accounts/worker_utils.py
    и backend/platforms/worker_utils.py): выбрать источник правды, второй —
    удалить или держать как тонкую обёртку. Иначе правки headless-флага и
    launch_context будут расходиться.
  - Разделить платформы по типу рантайма:
      * без браузера (YouTube API, Telegram MTProto через Telethon);
      * Playwright «фоновые воркеры» (TikTok, Instagram, X, Threads, Facebook,
        Rumble, Telegram Web — если используется);
      * интерактивные сценарии в accounts/settings_views.py.
    Для первой группы headless не важен; для второй — это и есть главная цель.

--------------------------------------------------------------------------------
Фаза 2 — Зависимости Chromium на Linux
--------------------------------------------------------------------------------

  - Установить Python venv на сервере так же, как в разработке (версия Python
    совпадает с проектом).
  - Выполнить python -m playwright install chromium в том же окружении, что у
    прод-процесса.
  - Выполнить python -m playwright install-deps (или поставить пакеты вручную
    по доке Playwright для вашей ОС).
  - Проверить переменную PLAYWRIGHT_BROWSERS_PATH (если ограниченный $HOME у
    systemd — путь должен быть доступен на чтение/запись).
  - Убедиться, что нет конфликта версий: Playwright из requirements и
    установленный browser build совместимы.
  - Если в каких-то воркерах остаётся browser_channel="chrome" — установить
    google-chrome-stable через apt (или аналог) И прогнать smoke-запуск на
    сервере. Иначе Playwright упадёт с «Executable doesn't exist».
  - Для force_persistent=True (Facebook, Telegram, Rumble и т.п.): подготовить
    writable каталог BROWSER_PROFILE_DIR под пользователя сервиса. Убедиться,
    что worker_pool не пытается открыть один и тот же persistent профиль из
    нескольких процессов — используются подкаталоги {platform}_persistent.
  - При нехватке памяти на маленьком VPS: заложить swap или лимит параллельных
    refresh. Ориентир: каждый активный daemon-воркер Chromium съедает
    ~300–600 МБ; Postgres и Django добавляют сверху. Прикинуть итог и
    количество одновременно работающих воркеров.

Фаза 5 — Упаковка деплоя
--------------------------------------------------------------------------------

ВАЖНО (общая оговорка):
  - Текущие backend/Dockerfile и docker-compose.yml — legacy, запускают
    `uvicorn app.main:app` (старый FastAPI). Это не актуальный рантайм
    проекта (live backend — Django через manage.py). Их нужно ПЕРЕПИСАТЬ
    под Django, а не использовать «как есть».

Docker (переписанный под Django):
  - Выбрать базовый образ: официальный Playwright (mcr.microsoft.com/playwright)
    или python:3.12-slim + ручная установка Chromium deps.
  - В Dockerfile: pip install -r requirements.txt, python -m playwright install
    chromium, python -m playwright install-deps.
  - CMD/ENTRYPOINT: gunicorn config.wsgi:application (или daphne для ASGI).
  - Предварительно: python manage.py migrate и при необходимости collectstatic
    на старте (entrypoint-скрипт), а не в слое образа.
  - Прописать ENV BROWSER_HEADLESS=true.
  - Смонтировать volume для BROWSER_PROFILE_DIR (persistent) и для БД, если
    Postgres крутится рядом.
  - Scheduler из accounts/apps.py: под gunicorn с N воркерами запускается
    в каждом процессе — дубли задач. Решения на выбор:
      * вынести scheduler в отдельный контейнер/процесс
        (например, `python manage.py run_scheduler`);
      * ставить gunicorn --workers 1 для процесса с scheduler;
      * lock через БД/файл.
    Зафиксировать выбранный вариант.
  - Проверить healthcheck и таймауты HTTP выше длительности refresh
    (refresh может быть минутами).

Без Docker:
  - Создать пользователя dashboard (не root).
  - Каталоги для кода, venv, BROWSER_PROFILE_DIR с правами этого пользователя.
  - systemd unit: EnvironmentFile=/etc/dashboard.env, WorkingDirectory,
    ExecStart на gunicorn (config.wsgi:application).
  - Отдельный unit для scheduler (или --workers 1 в веб-юните) — см. пункт
    про Docker выше; та же проблема дубликатов.
  - В dashboard.env: BROWSER_HEADLESS=true, DB_*, секреты, при необходимости
    PLAYWRIGHT_BROWSERS_PATH (если Chromium кладётся в нестандартное место).
  - logrotate или journald retention по желанию.

Фаза 6 — Запасной план при сбоях headless
--------------------------------------------------------------------------------

  - Для проблемной платформы: включить Xvfb (:99), в unit добавить ExecStartPre
    или обёртку xvfb-run.
  - Либо для одной платформы временно headless=False только под Xvfb
    (не на голом сервере без DISPLAY).
  - Либо вынести скрапинг этой платформы на отдельный worker с тем же образом
    Playwright.
  - Rumble (Cloudflare): если cf_clearance не проходит в headless —
    рассмотреть Scrapling (есть соответствующий skill в окружении) или
    ретраи с человеко-подобным поведением; как крайний вариант — headed
    под Xvfb.
  - Либо Browserless / CDP — отдельный сервис, в коде подключение по URL
    (если пойдёте этим путём — отдельный эпик).

Фаза 5V — Деплой на VPS (вариант A: свой порт, не трогаем 80)
--------------------------------------------------------------------------------

Контекст:
  - VPS: 146.103.120.54.
  - На 80 порту уже работает чужое приложение, не трогаем.
  - Свой стек поднимаем рядом, на 8080 (или любом другом свободном порту).

Артефакты в репо:
  - docker-compose.prod.yml     (production-overlay для VPS).
  - frontend/Dockerfile         (multi-stage: Vite build → nginx).
  - frontend/nginx.conf         (SPA + proxy /api,/admin,/static на backend).
  - backend/Dockerfile          (Playwright base + gunicorn).

Архитектура (всё в одной docker-сети `default`):
  - postgres   — внутри сети, наружу не торчит.
  - backend    — Django + gunicorn (--workers 1) + APScheduler
                 (RUN_SCHEDULER=true в этом же процессе) + Playwright Chromium
                 headless. `expose: 8000` — виден только из docker-сети.
  - frontend   — nginx со статикой Vite + reverse-proxy /api → backend:8000.
                 Маппится наружу: 8080 на хосте → 80 в контейнере.

Минимальные шаги на VPS:
  1. Установить Docker Engine + compose plugin (Ubuntu/Debian):
       curl -fsSL https://get.docker.com | sh
       sudo usermod -aG docker $USER && newgrp docker
  2. Открыть порт в firewall:
       sudo ufw allow 8080/tcp        # если используется ufw
  3. Склонировать репо в /srv/dashboard или ~/dashboard:
       git clone <repo-url> ~/dashboard && cd ~/dashboard
  4. Заполнить .env на основе .env.example:
       cp .env.example .env && nano .env
     Минимум для VPS:
       SECRET_KEY=<уникальный>
       DEBUG=false
       ALLOWED_HOSTS=146.103.120.54,localhost
       CSRF_EXTRA_ORIGINS=http://146.103.120.54:8080
       CORS_EXTRA_ORIGINS=http://146.103.120.54:8080
       DB_*=<свои>
       BROWSER_HEADLESS=true
       RUN_SCHEDULER=true
       BROWSER_PROFILE_DIR=/app/.browser-profile
       FACEBOOK_EMAIL/PASSWORD, TELEGRAM_API_ID/HASH/PHONE, YOUTUBE_API_KEY,
       INSTAGRAM_USERNAME/PASSWORD — по необходимости.
  5. Загрузить state-файлы (cookies) с локалки в volume browser_profile:
       docker compose -f docker-compose.prod.yml up -d postgres
       docker compose -f docker-compose.prod.yml run --rm backend bash
       # внутри: положить tiktok_state.json/instagram_state.json/... в
       # /app/.browser-profile/ через scp или ручной copy.
  6. Поднять весь стек:
       docker compose -f docker-compose.prod.yml up -d --build
  7. Проверка:
       curl http://localhost:8080/healthz       # nginx → 200 ok
       curl http://localhost:8080/healthz/      # backend → 200 {"status":"ok"}
       curl http://localhost:8080/api/accounts/ # backend через nginx-proxy
     Извне:  http://146.103.120.54:8080/

Обновление:
       git pull && docker compose -f docker-compose.prod.yml up -d --build

Если 8080 окажется тоже занят:
  - В docker-compose.prod.yml поменять "8080:80" на свободный, например
    "9090:80", и `ufw allow 9090/tcp`. На внутренний порт nginx (80) и
    BACKEND_UPSTREAM это не влияет.

Если решите подключить домен/HTTPS позже:
  - Добавить A-запись `dashboard.example.com → 146.103.120.54`.
  - На хосте поставить системный nginx, проксировать
    `dashboard.example.com:80/443` → `127.0.0.1:8080`, для HTTPS — certbot.
    Внутри compose ничего менять не надо, только обновить ALLOWED_HOSTS,
    CSRF_EXTRA_ORIGINS, CORS_EXTRA_ORIGINS.

Что НЕ делать:
  - Не выставлять `ports: 8000:8000` для backend — gunicorn должен быть
    доступен только из docker-сети, чтобы публичные запросы шли через
    nginx (который проверяет CORS и cap'ает body size).
  - Не запускать второй контейнер scheduler рядом с backend: оба пишут в
    один volume browser_profile, persistent profile Chrome не переживёт
    одновременную работу двух процессов.

Фаза 5R — Деплой на Railway (PaaS)
--------------------------------------------------------------------------------

Архитектура:
  - Postgres: Railway plugin (автогенерит DATABASE_URL).
  - Backend: один сервис (Docker image из backend/Dockerfile),
    gunicorn --workers 1 + APScheduler в этом же процессе (RUN_SCHEDULER=true)
    + Volume на /app/.browser-profile под BROWSER_PROFILE_DIR.
  - Frontend: отдельный сервис (multi-stage Vite → nginx, frontend/Dockerfile),
    публичный домен Railway.

Backend env (минимум):
  DJANGO_SETTINGS_MODULE=config.settings
  SECRET_KEY=<свой>
  DEBUG=false
  ALLOWED_HOSTS=<RAILWAY_PUBLIC_DOMAIN авто; добавьте кастомный домен>
  DB_SSL_REQUIRE=true
  BROWSER_HEADLESS=true
  RUN_SCHEDULER=true
  BROWSER_PROFILE_DIR=/app/.browser-profile

Frontend build args:
  VITE_API_URL=https://<railway-public-domain-of-backend>

Шаги:
  1. Создать проект Railway. Подключить GitHub-репозиторий.
  2. Postgres → Add Plugin → Postgres. Готово, DATABASE_URL появится в backend
     сервисе автоматически.
  3. Создать сервис Backend, Root Directory = backend/, Builder = Dockerfile.
     Подцепится backend/railway.json (healthz + start command).
  4. В backend сервисе: Volume → mount path /app/.browser-profile (≥ 1 GB).
  5. Создать сервис Frontend, Root Directory = frontend/, Builder = Dockerfile.
     В Build args указать VITE_API_URL = публичный URL backend (после п.3).
  6. Прокинуть {platform}_state.json (TikTok/Instagram/X/Threads/Facebook/Rumble)
     и при необходимости instagram.session/telegram.session через `railway run`
     (загрузка с локалки) либо одноразовый scp/curl в /app/.browser-profile.
  7. Healthcheck: backend → /healthz/, frontend → /healthz.

Ограничения, о которых нельзя забывать:
  - Эфемерный диск: всё, что вне Volume, теряется при редеплое.
  - Один Volume на сервис → именно поэтому scheduler крутится в backend, а не
    в отдельном сервисе.
  - HTTP таймаут Railway ~5 минут: refresh_all всех аккаунтов лучше не звать
    как один запрос; на фронте уже разбивается через refreshAccount/Bulk.
  - Telegram Web (headless=False) на Railway без Xvfb работать не будет.
    Используйте либо Telethon (MTProto) через TELEGRAM_API_ID/HASH/PHONE
    (без браузера), либо Telegram отключите.
  - Rumble + Cloudflare: при стабильных провалах на headless — кандидат на
    выпил из расписания или замену на Scrapling/CDP.


--------------------------------------------------------------------------------
Фаза 8 — Локальная разработка (Windows/macOS) после правок Railway
--------------------------------------------------------------------------------

Главная цель: всё, что добавлено для Railway, не должно ломать классический
локальный сценарий — `python manage.py runserver` + `npm run dev`.

Что было сделано, чтобы локалка осталась рабочей:

  - settings.py: STATICFILES_STORAGE = "whitenoise...CompressedManifestStaticFilesStorage"
    подключается ТОЛЬКО при DEBUG=False. В DEBUG=True Django сам отдаёт статику
    через staticfiles finders, collectstatic не требуется.
  - settings.py: DATABASES читает DATABASE_URL только если он непустой,
    иначе остаются прежние DB_* envs из backend/.env (Postgres локально).
  - apps.py / RUN_SCHEDULER: если переменная не задана, scheduler стартует
    как и раньше (поведение по умолчанию совместимо).
  - BROWSER_HEADLESS остаётся управляемым через .env. Локальное .env
    (BROWSER_HEADLESS=true) продолжает работать как раньше.
  - tiktok/worker.py и rumble/worker.py: `channel="chrome"` теперь дефолт ТОЛЬКО
    на Windows/macOS (sys.platform != "linux") — то есть локалка по-прежнему
    использует системный Google Chrome, а сервер на Linux — встроенный
    Chromium. Переопределяется через TIKTOK_BROWSER_CHANNEL / RUMBLE_BROWSER_CHANNEL.
  - frontend: `npm run dev` остаётся источником правды для разработки;
    vite.config.ts проксирует /api → http://localhost:8000.
    frontend/Dockerfile (nginx) используется только в проде/Railway.

Smoke-проверка после любых правок «деплойного» слоя:

  1. backend:
       cd backend
       .\.venv\Scripts\python.exe manage.py check
       .\.venv\Scripts\python.exe manage.py runserver
     Затем `curl.exe http://127.0.0.1:8000/healthz/` → 200,
     `/admin/login/` → 200, `/api/accounts/` → 200.
  2. frontend:
       cd frontend
       npm run build      # должен собраться без ошибок TS
       npm run dev        # http://localhost:5173 открывается, /api проксируется


--------------------------------------------------------------------------------
Критерии готовности
--------------------------------------------------------------------------------

  - С BROWSER_HEADLESS=true на Linux без установленного DE проходит refresh
    хотя бы для N из списка платформ (N согласовать).
  - Нет обязательной зависимости от физического монитора.
  - Повторный деплой с нуля по документу воспроизводит рабочее окружение.
  - Известны платформы-исключения (если есть) и для них есть план из Фазы 6.
